# Agents

Notes for AI agents working in this repo.

Future work is tracked in [ROADMAP.md](ROADMAP.md). Keep implementation notes
here and planned work there.

## Home Manager links

Home Manager owns the links into `~`. Actively edited trees are linked
out-of-store to this checkout by `nix/home/links.nix`, so editing a linked file
needs no switch, and adding or removing a linked file needs a `links.nix` edit
plus a `home-manager switch`. Static configs (git, ssh, atuin, direnv, procs)
are translated into modules under `nix/home/` and do need a switch to change.

**Generated theme artifacts are not committed**: Files produced by `./scripts/generate_colorscheme.sh` are local build artifacts and are gitignored. Do not edit or commit them; edit `palettes/*.lua` and the manual theme logic instead. Generate them on a fresh clone; the links to them may dangle until then.

**Avoid app-generated files leaking into the repo**: App-owned directories like `~/Library/Application Support/...` or `~/.claude` get file links inside a real directory, never a link to the whole directory. Otherwise files the app later writes there would show up as untracked files inside this repo. `nix/home/links.nix` follows this rule; keep following it when adding links.

Machine-specific committed config lives in the machine repos `../dotfiles-m1`
and `../dotfiles-gen-m5`, which consume this repo as a flake input. Each holds
its host's home and darwin layers plus its own out-of-store links: the Claude
`settings.json` and `machine.md`, the jj identity fragment, and on gen-m5 the
`~/.config/nvim-local` module and the starship variant config.

## Bootstrap and Auth

`install.md` holds the three-phase flow: phase 1 activates the base darwin
and home profiles (`.#base`) from a clone of this repo, with nix-homebrew
installing Homebrew itself during the switch; phase 2 authenticates with the
tools the base profile installed; and phase 3 clones the machine repo and
switches to the machine profiles. Two scripts remain:

- `scripts/auth.sh`: interactive account setup; handles GitHub CLI
  authentication, SSH key creation/loading, and 1Password CLI sign-in
- `scripts/link_google_drive.sh`: post-sign-in personal setup; discovers
  mounted Google Drive accounts and safely creates `~/drive-jaza` without
  committing an account identifier

If you change the flow, keep `install.md`, `scripts/auth.sh`, and `README.md`
in sync.

The public authentication Gist that predates the three-phase flow should point
at install.md if it is still published.

Selecting SSH through `gh auth login` is deliberate: GitHub CLI finds or creates
a key and uploads the selected public key as part of that login flow. Do not set
`git_protocol` to SSH through a non-interactive shortcut that skips key
registration.

`auth.sh` preserves the protocol of an existing GitHub login. A Home Manager
activation script clones missing tmux plugins from the `@plugin` declarations
without starting a server. The local Neovim review.nvim checkout is optional.

Package ownership is deliberate:

- `gh`, `1password`, and `1password-cli` are in the shared darwin module so
  the phase 1 base switch installs them before phase 2 authenticates.
- Global tools and toolchains belong to Home Manager (`nix/home/tools.nix`),
  including mise, which stays project-local in use: there is no global mise
  config.
- Common applications, including Discord and Zulip, belong only to the shared
  darwin module; machine repos declare only machine-specific additions.

Software ownership should remain actionable rather than becoming a second
inventory:

- common Homebrew casks and App Store apps belong in `nix/darwin/homebrew.nix`
- machine-specific casks and App Store apps belong in the machine repo's
  `darwin.nix`
- genuinely manual software needed on a fresh personal machine belongs in the
  README post-install checklist
- helper apps generated by a declared parent application, such as Google
  Drive's Docs/Sheets/Slides shortcuts, are not declared separately
- current-state audits belong in command output or the future `doctor`
  operation, not in a committed snapshot that will immediately drift

Google Drive is installed by the shared darwin module, but its account-specific
mount does not exist until the user signs in. The README therefore invokes
`scripts/link_google_drive.sh` in the post-install checklist. Keep account
emails and CloudStorage directory names out of committed scripts and machine
metadata.

## Public Repo Hygiene

This repo is intended to be public. Do not commit host-specific SSH entries, private hostnames, IPs, usernames, ports, proxy rules, tokens, or other secrets.

Secrets stay out of every repository and out of the Nix store. They live in
uncommitted local files that committed config sources
(`~/.config/shell/env.local.sh`, `~/.ssh/config.local`), and 1Password is the
source of truth, resolved by a machine repo's `scripts/setup-secrets.sh`
rather than by sops. SSH private keys are per-machine and
passphrase-protected, are held by the macOS Keychain-backed agent, and are
never synced through 1Password.

The SSH config in `nix/home/ssh.nix` should stay limited to public defaults,
the `github.com` host block, and the `Include ~/.ssh/config.local` directive.
Put private hosts in that ignored local include. The common Git config in
`nix/home/git.nix` carries no identity; each machine repo sets
`programs.git.settings.user` and the jj `conf.d` fragment, so no identity is
committed here.

## CI and updates

`.github/workflows/ci.yml` runs on push and PR and is evaluation-only, since
evaluation is platform-independent: Ubuntu runners force the module system
through `nix eval .#darwinConfigurations.base.system.drvPath` and the
`homeConfigurations.base` activation package, a lint job runs shellcheck over
`scripts/` and the shell tree plus `stylua --check` over the nvim lua, and a
tests job runs the `tests/*.lua` checks through a headless nixpkgs neovim and
`tests/setup.sh`. Nothing mac-specific is built, though `macos-14` arm64
runners are free on a public repo if evaluation ever misses breakage.

Renovate's GitHub App keeps `flake.lock` and the workflow pins current here
and in `../dotfiles-m1`, and automerges only on green CI. There is no branch
protection, because it would block direct pushes to main and Renovate waits
for green checks anyway. `lazy-lock.json` updates through the weekly
`.github/workflows/nvim-lock-update.yml` instead, which runs the config's own
`nvim --headless "+Lazy! update"` and opens a PR scoped to the lock, so no
plugin-name-to-repo mapping table has to be maintained. There are no release
tags: the machine repos track this repo's main branch, so a core change
reaches a machine after a push plus that machine's next lock refresh, or
immediately with `nix flake update dotfiles` there. `gen-m5`'s updater and CI
live on the work side, since its base-flake input needs the work netrc.

## Nix architecture decisions

The Nix design follows
[flakes aren't real and cannot hurt you](https://jade.fyi/blog/flakes-arent-real/):
the flake is an entry point with a pinning system, and everything else uses the
ordinary primitives (functions, overlays, modules).

- `flake.nix` stays a thin entry point that pins inputs and exports modules
  and host configurations. It contains no logic.
- This public repository holds the reusable modules (`homeModules.*`,
  `darwinModules.*`, later `nixosModules.*`) plus the machine-free base
  bootstrap profiles (`darwinConfigurations.base`, `homeConfigurations.base`)
  for install.md phase 1. Every machine has its own repository that imports
  the core and holds its host composition. Consumers import modules and set
  options.
- Input overrides and `specialArgs` are not part of the API, since
  `specialArgs` does not compose across flakes. Anything a module needs
  arrives through `pkgs`, options, or lexical closure in the entry point.
- Configuration flows through module options. Use upstream Home Manager and
  nix-darwin options and their merge semantics wherever they exist, for
  example `programs.git.includes`, `programs.ssh.settings`, and `homebrew.*`.
  Define `dotfiles.*` options only where no upstream option fits.
- Pins match the work base flake: nixpkgs `nixos-26.05`, Home Manager
  `release-26.05`, and the nix-darwin release branch for the same nixpkgs
  release. Upgrade when the work base flake moves. Consumers track the
  core's main branch and move by lock refresh; releases are not tagged.
- flake-parts and the dendritic pattern are not adopted here. Revisit only if
  the flake output layer grows past a screen of per-system boilerplate.
- Modules never fetch at evaluation time. Pinned dependencies enter through
  flake inputs at the entry point only.
- Home Manager feature modules stay platform-neutral where reasonable and
  must work under nix-darwin, NixOS, and standalone Home Manager. The work
  machine uses the standalone mode.
- The machine repos own machine facts: username, home directory, hostname,
  and profile choices. No module here may hard-code `jsyed` or a home path,
  except the base bootstrap outputs in `flake.nix`, which hard-code the
  username by decision, since the core is the personal base and the name is in
  its history regardless.
- Actively edited configuration (nvim, shell startup, sketchybar, the Claude
  directory, generated themes) stays as plain files linked out-of-store, so
  editing a file needs no switch. Home Manager owns only the links and
  packages.
- Work integration: `../dotfiles-gen-m5` (pushed to the work GitLab) holds
  both the `jsyed@gen-m5` standalone Home Manager layer and
  `darwinConfigurations.gen-m5`. It owns all work-specific configuration;
  the core owns ergonomics and stays free of work config.

## Repository layout

The top-level directories mirror paths below `$HOME` and are linked
out-of-store by `nix/home/links.nix`:

| Package | Contents |
|---|---|
| `shell` | Shared environment and interactive shell config (Home Manager links) |
| `zsh` / `bash` | Shell entrypoints (Home Manager links) |
| `claude` / `pi` | Coding-agent configuration (Home Manager links) |
| `aerospace` / `sketchybar` / `hammerspoon` | macOS window/UI automation (Home Manager links) |
| `nvim` / `vim` | Editor configuration (Home Manager links) |
| `wezterm` / `tmux` / `starship` | Terminal and prompt configuration (Home Manager links) |
| `typora` | Generated local theme assets (Home Manager links) |

Shell configuration is layered as follows:

- `shell/.config/shell/env.sh`: shared PATH/environment, sourced by
  `zsh/.zshenv` and `bash/.profile`
- `~/.config/shell/extra.env.sh`: machine environment written by the
  `dotfiles.shell.extraEnv` option, set in the machine repo
- `shell/.config/shell/env.local.example.sh`: example for the ignored
  `~/.config/shell/env.local.sh`
- `shell/.config/shell/interactive.sh`: shared aliases/functions/tool init,
  sourced by `zsh/.zshrc` and `bash/.bashrc`
- `~/.config/shell/extra.interactive.sh`: machine aliases/functions written by
  the `dotfiles.shell.extraInteractive` option, sourced after shared
  interactive config

Generated completions live outside the repository at
`${DOTFILES_COMPLETIONS_DIR:-$HOME/.cache/dotfiles/completions}`. Every
`home-manager switch` regenerates them through an activation script in
`nix/home/activation.nix`, which also installs the tmux terminfo entry and
clones missing tmux plugins. Rebuild completions by hand after installing,
removing, or upgrading supported tools:

```sh
./scripts/generate_completions.sh
exec zsh # or: exec bash
```

Add a generator to `scripts/generate_completions.sh` for any tool whose
package ships no completion, whatever the owner; nixpkgs-shipped completions
load from `~/.nix-profile/share/zsh/site-functions` on fpath.

Home Manager is flake-based and owns the Nix-specific package set, including
tmux with sixel support. The package set lives in `nix/home/tools.nix`, and
the per-machine user layers are `homeConfigurations` targets in the machine
repos (`jsyed@m1` in `../dotfiles-m1`, `jsyed@gen-m5` in
`../dotfiles-gen-m5`). Nix itself is a setup prerequisite. Apply with
`home-manager switch --flake <machine-repo>#jsyed@<machine>`, or bootstrap
through `nix run home-manager/release-26.05` when the CLI is not installed
yet. Roll back by running a previous generation's `activate` script from
`home-manager generations`. Do not commit `~/.config/nix/nix.conf` or
`~/.config/nix/netrc`.

## Changing theme colors

Colors are managed through a single-source-of-truth system. Palette files in `palettes/` define all colors, and a generator produces local, gitignored configs for each themed app, including shell `fzf`.

1. Edit the palette in `palettes/<name>.lua`
2. Update highlight group mappings in `nvim/.config/nvim/lua/colors/init.lua` if needed
3. Run `./scripts/generate_colorscheme.sh` to rebuild the local theme artifacts
4. Existing artifacts flow through the out-of-store links with no further step.
   If the generated file set changed, add the per-file links (aerospace, shell
   fzf themes, typora) to `nix/home/links.nix` and run `home-manager switch`

Theme-switching behavior is documented below.

### Adding a new theme

1. Create `palettes/<name>.lua` with a unique `bg` hex
2. Run `./scripts/generate_colorscheme.sh`
3. Add the new per-file links (aerospace mode-borders, shell fzf theme, typora
   CSS) to `nix/home/links.nix` and run `home-manager switch`; the nvim, tmux,
   wezterm and pi artifacts sit under directory links and need nothing
4. Update the theme architecture section below if user-facing switching
   behavior changes

The generator validates the palette schema, rejects duplicate `bg` values, and
writes Neovim's background registry, so there is no manual registration step.

## Theme architecture

Palette files in `palettes/*.lua` are the build-time source of truth.
`./scripts/generate_colorscheme.sh` turns them into app-specific artifacts for
Neovim, WezTerm, tmux, shell `fzf`, AeroSpace/JankyBorders, Pi, and Typora.

### Runtime state model

Theme state has deliberately different scopes:

- `DOTFILES_THEME`: shell-process state, also stored in a tmux session
- tmux `@theme`: session-scoped state
- WezTerm user-var `THEME`: window-scoped state
- Neovim colorscheme name: process-scoped state

### Build layer

Built-in palettes are `dark`, `light`, `ft`, `flexoki_dark`, and
`flexoki_light`. Flexoki is adapted to this repository's smaller palette
schema, so it intentionally omits some official colors/shades.

For each palette, the generator writes:

- `nvim/.config/nvim/lua/colors/<name>.lua`
- `nvim/.config/nvim/colors/colors_<name>.lua`
- `wezterm/.config/wezterm/colors_<name>.lua`
- `tmux/.config/tmux/colors-<name>.conf`
- `shell/.config/shell/fzf-theme-<name>.sh`
- `aerospace/.config/aerospace/mode-borders-<name>.sh`
- `pi/.pi/agent/themes/<name>.json`
- `typora/.../themes/<name>.css`

Across all palettes the generator also writes
`nvim/.config/nvim/lua/colors/registry.lua`, the bg hex → theme name registry,
and `palettes/manifest.txt`, the list of generated artifacts. A later run
prunes manifest entries it no longer generates. Typora CSS is rendered from
`palettes/typora.css.template`.

Generated files are local, ignored artifacts. Never edit or commit them.
Regenerate them with `./scripts/generate_colorscheme.sh`. The installer runs
the generator during fresh-machine setup. Update `nix/home/links.nix` and
switch only when the generated file set changes.

Neovim normally uses `DOTFILES_THEME` at startup. The generated background-hex
registry in `nvim/.config/nvim/lua/colors/registry.lua` exists only for OSC 11
fallback/manual redetection.

### Runtime propagation

Interactive shell startup resolves a theme in this order:

1. `DOTFILES_THEME`
2. tmux session `@theme`
3. the active WezTerm window's theme file
4. `light`

It sources `fzf-theme-<name>.sh` and exports `DOTFILES_THEME`. The `theme
[query]` helper resolves candidates from generated fzf theme files: no query
opens an inline picker, an exact or single partial match applies immediately,
multiple matches open the picker, and no matches print the available themes.
Applying a theme updates shell-local fzf state, exports `DOTFILES_THEME`, sends
WezTerm a `THEME` user-var escape, and, inside tmux, invokes
`~/.config/tmux/apply-theme.sh` for the current session.

WezTerm boots with the generated light palette. Its `user-var-changed` handler
applies `THEME` as window color overrides. Tabs in one window share a theme;
different windows can differ.

tmux starts with `@theme='light'` and `colors-light.conf`. New sessions import
the creating client's `DOTFILES_THEME` as a hint.
`~/.config/tmux/apply-theme.sh` resolves session `@theme`, then session
`DOTFILES_THEME`, then `light`; writes both session values; applies the generated
colors to the session/windows; and rebuilds the statusline. Session/window hooks
reapply it so new UI surfaces remain aligned.

Neovim reads `DOTFILES_THEME` at startup and preserves the active `colors_*`
scheme across config reload. Without the variable, `UIEnter` queries OSC 11,
maps the returned background through `M.registry`, and applies the matching
theme. Manual redetect uses the same path.

Pi receives generated JSON themes and a global startup extension through the
`pi` package. The extension applies `DOTFILES_THEME` when it names a loaded
theme; manual Pi settings remain available otherwise.

Consequently, fzf changes affect the current shell and children; existing tmux
sessions retain their session theme; WezTerm is window-scoped; Neovim and Pi
follow the launching shell at process/session startup.

## Neovim architecture

The Neovim config has a small startup core, reloadable editor settings,
filetype-local policy, and a custom Alabaster colors/highlighting system:

```text
nvim/.config/nvim/
├── init.vim                  # Vimscript shim into Lua startup
├── lua/
│   ├── init.lua              # lazy.nvim bootstrap, plugins, editor setup
│   ├── settings.lua          # reloadable settings entry point
│   ├── config/
│   │   ├── editor.lua        # LSP/lint/completion orchestration
│   │   ├── lsp/              # native vim.lsp setup and attach policy
│   │   ├── options.lua       # core options
│   │   ├── keymaps.lua       # global keymaps
│   │   ├── autocmds.lua      # non-filetype global autocmds
│   │   ├── diff_windows.lua  # shared diff-pane highlights/scroll focus
│   │   ├── dropbar.lua       # dropbar sources, abbreviations, menu keys
│   │   ├── markdown.lua      # markdown extmarks/window behavior
│   │   ├── projects.lua      # shared project path detection
│   │   ├── reload.lua        # lifecycle registry and <leader>cr reload
│   │   ├── string_masks.lua  # shared string-whitespace mask engine
│   │   └── window_move.lua   # sticky window layout movement mode
│   └── colors/
│       ├── init.lua          # colorscheme API/highlights
│       ├── registry.lua      # generated bg hex → theme registry
│       ├── util.lua          # color math
│       └── windows.lua       # markdown/zen/diff namespaces
└── after/
    ├── ftplugin/             # filetype-local policy
    └── queries/*/            # Treesitter query extensions
```

`init.vim` loads `lua/init.lua`. Startup bootstraps lazy.nvim, registers plugin
specs, configures integrations through `config.editor`, and loads
`settings.lua`. `config.reload` holds the one ordered lifecycle registry:
`config.editor` and `settings.lua` derive their setup sequences from it, and
`<leader>cr` derives invalidation from it, runs teardown hooks, re-runs editor
integrations, and reloads settings. Plugin specs and lazy.nvim bootstrap are
intentionally outside the reload boundary. Dropbar configuration lives in
`config.dropbar` and is restart-only, though it re-requires `config.projects`
and `config.machine` at call time so path policy follows a reload.

The Python, YAML, and Nix string-whitespace maskers share one engine in
`config.string_masks`. Each language module supplies its query, and Nix also
supplies its common-indent rule, since Nix indented strings keep indentation
beyond the shared margin as content. Wrappers around plugin internals (cmp
float placement, difftastic split direction, the mypy linter) keep the
pristine function on the plugin module and are rebuilt over it on every
setup, so a reload cannot stack wrappers.

LSP, lint, and completion live outside `init.lua`: `config.lsp` owns native LSP
servers/attach policy, `config.lint` owns nvim-lint and project-specific mypy,
`config.completion` owns nvim-cmp, and `config.projects` centralizes project
detection. Machine-specific policy comes through `config.machine`, no-op
defaults over the optional `machine` module that a machine repo links onto the
runtimepath at `~/.config/nvim-local`.

Buffer-local language policy belongs in `after/ftplugin/`; global autocmds stay
in `config.autocmds` only when not naturally filetype-local. Generated palette
modules live under `lua/colors/`; highlight definitions, color math, window
namespaces, and Treesitter overrides remain separated as shown above.

`<leader>wm` enters the sticky window move mode owned by
`config.window_move`. Lowercase `hjkl` reorders the active window through the
layout, uppercase `HJKL` changes its nesting level through Tradewinds, and
`Escape`, `q`, or `Ctrl-C` exits. Lualine shows the active mode and its key
hint while input is captured.

Light-theme syntax background tints are suppressed with window-local
highlight namespaces in Markdown and in the code panes of Diffview+ and
Difftastic; syntax foregrounds and the viewers' own diff highlights remain.
Colorful WinSep gives the focused Neovim split a high-contrast active edge
drawn with double lines, so it reads as nested inside tmux's heavy pane
borders; its `ColorfulWinSep` highlight follows the active palette.
Both diff viewers use the shared scroll-bound window helper so mouse-wheel
events over an unfocused pane focus it before native scrolling is processed,
keeping the panes synchronized. Difftastic view creation temporarily enables
`splitright` so its semantic old/new windows are physically old-left/new-right,
then restores the user's global split policy.

Project-specific LSP initialization is derived per client through the machine
module's `before_init`; Rust rooter corrections are window-local.
Reload reconstructs attach policies for existing clients as well as future
attachments. Signature-help responses are accepted only for the latest request
at its original buffer, window, cursor, change tick, and insert mode.
